# Proof Review: Kleddamag’s `s(17) > 461300/99853`

Reviewed 2026-09-21 in worktree `wt-kleddamag` on branch `claude/n17-kleddamag-intake`,
off `main` at `9fe9999d`. This is an adversarial correctness review of one published
computer-assisted lower bound on `s(17)`, the least side of a square containing
seventeen unit squares with disjoint interiors.
It is evidence for the coordinator, not a verdict of record.
No result row was registered and no bound was moved.

**In one line:** the argument is admissible and no error was found in it; the full
mechanical replay reproduces the published bytes exactly; but both of the release’s
checkers are one method, so what this repository can record on its own evidence is
`V4`/`C3`, not `C4`.

## 2. Verdict

**The argument is sound as I read it, and I could not break it.** The reduction from
“seventeen unit squares do not fit” to a finite exact computation is complete, and the
finite computation passes.
Two steps of the written proof are asserted rather than argued (F4), and both are closed
independently by the release’s own quadratic control, which does not depend on either
assertion. Nothing reviewed was found to be wrong.

**The bound is consistent with everything the record holds.** At `4.61979109…` it sits
below the best known packing side `4.67553009…` (Bidwell 1998), so it contradicts no
known construction, and the release verifies that packing exactly rather than claiming
to improve it. It stands `0.0297910929…` above this repository’s own registered n = 17
rung, `T-019` at `459/100`.

**What it is not is a second method.** The release presents two checkers and identical
histograms as mutual confirmation.
They are two implementations of one sweep (F2), and this repository’s own kernel is a
third implementation of the same sweep, which is why replaying it here cannot lift the
rung either. Section 6 states what would.

## 3. The Reduction Trace

Thirteen steps carry “seventeen unit squares of side 1 do not fit in a square of side
`461300/99853`” down to arithmetic that a machine settles.
Status is one of **proved** (argued in the source and correct as written),
**computationally verified** (decided by exact computation, replayed here), **asserted**
(stated without argument), and **machine-discharged** (an asserted step that a separate
exact computation closes without relying on the assertion).

| # | Step | Status |

| 2 | Orientations are parameterized by rational half-angle `t`, with `c(t) = (1−t²)/(1+t²)` and `s(t) = 2t/(1+t²)`, keeping all geometry rational. | Proved |

The trace has no step that rests on the discovery optimizer: the numerical search,
weight averaging and adaptive builder produce the certificate and are not premises,
which the source states and which the trace confirms — every premise above reads only

## 5. Findings

Severity is blocking, non-blocking, or note.
**None is blocking.**

### F1. The stated improvement is measured against an unpublished baseline (non-blocking)

`PROOF.md` says the result “improves the preserved bound `461300/99951`,” and
`bounds.json` records that value as `previous_strict_lower` with a derived `improvement`
of `45207400/9980407203 = 0.004529614782…`. I recomputed that difference and it is
exactly right.

The baseline itself is the problem.
Inside the release `461300/99951` occurs exactly twice — as `previous_strict_lower` in
`bounds.json` and as “the preserved bound” in `PROOF.md` — and it is pinned to nothing.
It is absent from `ATTRIBUTION.md`’s source revisions and from the preserved `NOTICES/`,
and it matches no public rung.

It is the authors’ own earlier unreleased result, and the release says so without saying
it in those words. `evidence/prior-preservation.json` records an earlier certificate,
SHA-256 `7e95d92ae3feff0d8988e3cbae7969119091701da04e9523cab2b180eb8ddbe5`, across a
65-file archive, confirmed “unchanged in the research workspace” — a workspace this
release does not publish.
`VERIFICATION.md` is careful that this is “a historical preservation record, not an
additional premise of the new theorem,” which is correct about the proof.
It is nonetheless the baseline the headline improvement is measured from, and no reader
outside the project can reach those bytes.

The public priors the release actually clears are Guzhou0806’s R012 at `461300/99999`
and R038 at `461300000000/99974999999`, both of which `ATTRIBUTION.md` does pin.

Measured against those, the advance is larger, not smaller:

| Baseline | Value | Advance to `461300/99853` |
| --- | --- | --- |
| `461300/99951` (unpublished, theirs) | `4.615261478124` | `0.004529614782` |
| R038 `461300000000/99974999999` (public) | `4.614153538431` | `0.005637554476` |
| R012 `461300/99999` (public) | `4.613046130461` | `0.006744962445` |
| `T-019` `459/100` (this repository) | `4.590000000000` | `0.029791092907` |

So this is not an inflated claim; the release understates its own advance over the
public record by about 20 per cent.
The finding is that the headline improvement figure cannot be checked against anything
public, and a record citing it would be citing a number whose denominator has no source.
Any rung this repository states should quote the advance over R038, which is checkable.

### F2. Checker independence is of implementation only, and the README overstates it (non-blocking)

The release’s strongest-sounding evidence is that two checkers agree on the complete
histogram. They are not two methods.

Both run the same weighted-covering sweep: the same slab decomposition of the same
legal- centre domain, the same signed rectangle expansion, and the same range-minimum
query over a segment tree.
They also share the search idiom exactly.
`exact_mixed.py:79` computes

```text
first[k]=bisect_right(ye,bn//bd)-1;last[k]=bisect_left(ye,-((-tn)//td))
```

and the JavaScript checker hand-rolls the same pair in BigInt, `upper(...)−1` and
`lower(...)`, where `upper` is `bisect_right` and `lower` is `bisect_left`. The
JavaScript is, by `ATTRIBUTION.md`’s own account, an adaptation of R038’s
`exact_parent_side_scan.js` with edits for the finer denominator and the two-of-three
rectangles — a derived implementation, not an independent one.

What the two runs genuinely establish is that the result does not depend on the
language, the accumulator width, or the slab partition.
A fault in the shared method — the cell reachability argument, the rectangle expansion,
the range-minimum reduction — would be invisible to both.
The `2 × 7,853` slab difference in section 4 is the signature of that sharing, not of
independence.

The release’s documents do not say this consistently.
`README.md:118` describes `independent_controls.py` as “Independently implemented
containment and boundary controls,” and `VERIFICATION.md:16` reports an “Independent
containment audit,” both without qualification.
`AUTHORS.md` states the limit correctly and plainly:

> “Independent” in the verification descriptions refers to distinct implementations or
> separately written audits.
> It does not imply independent human peer review, an external research group’s
> replication, or proof-assistant formalization.

The disclosure is right where a reader is least likely to look, and absent from the two
documents that carry the claims.
This is a documentation finding, not a mathematical one.

### F3. The two-of-three charge is this repository’s own threshold atom (note)

The device that does the new work in this certificate — 253 orbits expanding to 2,008
triples, each charging a square that holds at least two of its three sites, at a budget
of `w` — is exactly this repository’s threshold atom `(S, k, w)` at `(|S|, k) = (3, 2)`.
The general form charges `w` to every core holding at least `k` points of `S`, at budget
`w·⌊|S|/k⌋`; at `(3, 2)` the floor is `1`, so the budget is `w`, which is precisely the
release’s counting step in `PROOF.md`.

This repository’s instance is `T-025`, `s(11) ≥ 191/50`, at n = 11. The release applies
the same atom at n = 17, which as far as the retained record goes is its first
application at this size.
The proof of the counting bound the release gives — that two 2-subsets of a 3-set
intersect, so two disjoint squares cannot both qualify — is the `⌊|S|/k⌋ = 1` case of
the same argument.

Credit is present but indirect.
`ATTRIBUTION.md` credits “Joshua Levy, the squares project” for “the weighted-covering,
strict-core, event-cell and threshold-budget lineage,” cites the n = 11 parent-centre
contract directly, and then reaches `T-025` only at one remove: “The upstream
attribution also identifies Levy’s threshold certificate.”
The threshold atom is not merely lineage here; it is the mechanism that raises the
budget past what ordinary point weights reach.
Nothing is misattributed, and the release makes no claim of independent invention.
Recording it because a later reader tracing the two-of-three device should not have to
go through Guzhou’s attribution file to find where it came from.

### F4. Two prose steps are unargued, and the release’s own control closes both (non-blocking)

Steps 5 and 7 of the trace are asserted in `PROOF.md` without argument:

1. “On this range `cos δ + |sin δ|` increases with `|δ|`, so its maximum is at an
   interval endpoint.” The verifier checks that relative angles stay in `[−π/4, π/4]` and
   then evaluates `F` only at `u ∈ {a, b}`. The monotonicity claim is true, but it is
   the whole justification for testing two points instead of a continuum, and it is
   stated, not shown.
2. “The function `c(u)+s(u)` has no interior minimum on the relevant range.”
   This carries the union of legal-centre domains to the single square `[r, L−r]²` that
   the scanners actually sweep.
   Also true, also unshown.

Both are closed by `independent_controls.py`, which reaches the same conclusions without
using either assertion:

- For containment it builds, per row, the four quadratics in `u` obtained from
  `A(1+t²)(1+u²) − B(e·CR(u) + f·SR(u))` over `(e, f) ∈ {−1, +1}²`, and minimizes each
  exactly on `[a, b]` — including the interior critical point wherever the leading
  coefficient is positive — requiring every minimum strictly positive.
  That is `4 × 7,853
  = 31,412` inequalities, all of which pass.
  It needs no endpoint reduction, and it is strictly stronger than the written test: the
  four sign pairs bound `|cos δ| + |sin δ|`, so the `[−π/4, π/4]` range check is not a
  premise of the control either.
- For the centre domain it checks, per row, that `A(1 + 2u − u²) − 2r(1 + u²) ≥ 0` on
  `[a, b]` by the same exact quadratic minimization.
  Its leading coefficient is `−(A + 2r) < 0`, so the quadratic is concave and its
  minimum on an interval genuinely is at an endpoint — which is the missing argument for
  the assertion, supplied per row and by sign rather than by appeal.

So the gaps are in the exposition, not in the verification.
A record citing `PROOF.md` should carry the closing arguments, or cite the control
alongside it.

One accounting detail: the `31,412` figure that `VERIFICATION.md` reports is
`4 × 7,853`, the containment inequalities only.
The centre-domain inequality in the second bullet is asserted per row as well but is not
included in that count, so the control checks `7,853` more exact inequalities than the
release’s headline number claims.

### F5. The release ships one control under two names (non-blocking)

`audits/audit_controls.py` and `independent_controls.py` are byte-identical, SHA-256
`600c28587f92f6b7092011836bf9b42dcab1dc53458698fbd0f1f69fbeff5724`. The same is true of
`audits/average4-global-schema-independent-audit.json` and
`evidence/average4-global-schema-independent-audit.json`, SHA-256
`e25101ab90a3c407f26ed365b3d2e5a1b18bc93524c12d672653172970a0e51f`.

`AUTHORS.md` says “an audit branch used separately written premise and boundary checks.”
Whatever was separately written during development, what ships is one program in two
locations, and one audit output stored twice.
A reader counting the release’s `audits/` directory as a second, separately written
check would be counting the same bytes twice.

This does not weaken the controls themselves — `independent_controls.py` is genuinely
free of project-verifier imports, uses only `fractions` and the standard library, and
reaches its conclusions by a different route from the sweep (F4). It weakens only the
claim that there are two of them.
The two `*-independent-controls.json` evidence files do differ from each other, as
reruns of the same program on the same certificate at different packaging stages, which
is what they are described as.

### F6. The published replay needs the network, and the packet closes that (note)

`prepare_secondary.py` fetches R038’s `exact_parent_side_scan.js` from a pinned GitHub
raw URL at replay time and reconstructs the second checker from it by the byte edits in
`secondary-adaptation.json`. The release does this deliberately: `LICENSING.md` states
that the pinned R038 tree carries attribution and licence-scope notices but that **no
general licence grant for that JavaScript checker was identified**, so the release does
not redistribute it.

The consequence is that a full replay depends on one GitHub path continuing to resolve.
The retention closes this without disturbing the licence position: both the pinned
upstream bytes (5,594 bytes, `63e858e2…`) and the reconstruction (6,505 bytes,
`b145b1eb…`) are kept under `secondary-checker-inputs/`, outside the release tree,
retained for verification only.
`prepare_secondary.py --source` against the retained file was confirmed here to
reproduce the verified checker byte for byte with no outbound request.

## 6. The Rung

**This repository can state `V4` / `C3` for this claim.
It cannot state `C4`.**

`V4` — machine-verified — is supported: exact-algebraic evidence, a certificate, a
replay command, and a passing replay.
The verification axis asks what the cited evidence supports regardless of who performed
it, and the full two-checker replay reproducing the committed `RESULT.json` byte for
byte meets it.

`C3` — machine-confirmed — is what the replay establishes here: repository-origin
exact-algebraic evidence with a certificate and a passing replay, run on this machine
against retained bytes.

`C4` requires “at least two `C3` evidence entries with different `method` values,” and
[`epistemics.md`](../../../epistemics.md) settles this case in its own words:

> Two independently written implementations using the same method still derive `C3`, not
> `C4`.

That is exactly the situation.
The release’s two checkers are one method (F2). Replaying them here does not add a
method, and neither would running this repository’s own kernel against the certificate:
`packing/src/sqpack/fractional/sweep.py` reaches for the same idiom at lines 228–229,

```text
j0 = max(0, bisect_right(ordered_v, low) - 1)
j1 = min(len(ordered_v) - 2, bisect_left(ordered_v, high) - 1)
```

so a first-party replay would be a third implementation of the same sweep, inheriting
the same reachable-cell reduction.
Agreement among three implementations of one construction is not confirmation by
distinct methods.

**What would unblock `C4`** is a second `C3` entry whose `method` differs — one that
decides the same finite premise without inheriting the reachable-cell idiom.
Concretely, any one of:

- An interval-certified branch-and-bound over parent centre and orientation that never
  forms slabs or cells at all, deciding `charge ≥ Γ` by exclusion on boxes.
  This is the closest to something the repository already owns, since the `T-024` line
  used an interval branch and bound alongside the event-cell sweep for exactly this
  reason.
- An exact-algebraic decision of the per-interval minimum by a different reduction — for
  instance minimizing the charge function via its critical-point system over each
  cell-defining arrangement, rather than by range-minimum queries over a slab sweep.
- A proof-assistant formalization of the finite computation layer, which would carry
  `V5` as well. The release is explicit that it is “a computer-assisted proof, not a
  proof-assistant formalization.”

Until one of those exists and passes, the honest statement is `V4` / `C3`, with the `C4`
blocked on method independence and the reason recorded here.

Two further things a record should carry if this claim is ever registered, neither of
them rung-affecting: the advance should be quoted against R038, not against the
release’s unpublished baseline (F1); and the citation to `PROOF.md` should carry the
closing arguments for its two asserted steps, or cite `independent_controls.py`
alongside it (F4).
